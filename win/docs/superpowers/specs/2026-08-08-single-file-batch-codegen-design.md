# Mira 单文件批处理代码生成设计

## 目标

优化单个 `.mira` 文件从冷启动到可执行文件生成的完整耗时，不依赖后台
服务、多文件摊销或跨次增量缓存。第一阶段以 `bench/gen_800.mira -O3` 为
主门槛：3 次预热、31 次正式样本的中位数从约 694 ms 降至 250 ms 以下。

必须同时满足：

- `gen_100.mira -O3` 完整编译时间不得退化超过 1%；
- 100、200、400、800 函数规模的增长曲线不得出现新的超线性区间；
- 现有运行基准不得出现可复现退化；
- 产物体积不得增长超过 1%；
- Windows x86-64 与 Linux/SysV 均通过；
- 不针对文件名、函数名、基准内容或固定常量写规则。

## 当前证据

Windows 正式编译器 5.13.4、Mira `-O3` 与 Go 默认优化，3 次预热和 31 次
正式样本：

| 函数数 | Mira | Go | Mira/Go |
|---:|---:|---:|---:|
| 100 | 49.233 ms | 247.827 ms | 0.199 |
| 200 | 89.007 ms | 245.244 ms | 0.363 |
| 400 | 221.933 ms | 238.490 ms | 0.931 |
| 800 | 693.966 ms | 243.674 ms | 2.848 |

细分计时显示 800 函数 O0 总计约 306 ms，其中 codegen 约 229 ms；O3
总计约 668 ms，其中 codegen 约 591 ms。解析约 18--19 ms，链接约
22--23 ms。因此第一阶段处理 codegen 内的全局重复工作，而不是文件读取、
解析器或链接器。

## 方案选择

### 采用：批量索引，然后融合模块事实扫描

编译开始时一次建立模块函数索引和调用事实。SSA builder、内联器、引用检测
和未引用函数删除通过索引查询，不再针对每个调用点或函数重复线性扫描整个
函数数组。索引收益稳定后，再融合生命周期相同的模块事实扫描。

这是首选方案，因为它直接消除 `函数数 × 调用数` 的重复工作，O0--O3 都能
获益，且不改变优化决策。

### 暂不采用：直接融合所有 SSA pass

大量函数级 pass 确实会重复遍历 IR，但不同事实的失效边界不同。立即融合会
扩大正确性风险，并难以判断每项收益。只有经过细分计时证明为剩余主热点，且
事实共享同一 SSA 版本时才融合。

### 暂不采用：函数级并行

线程池可能提高多核吞吐，但无法修复平方级算法，在老机器上收益也不稳定。
第一阶段保持单线程和确定性；批处理索引完成后再单独设计并行方案。

## 架构

新增独立的模块索引单元 `codegen/ssa_function_index.c`，对应声明放在
`codegen/ir_ssa.h`。核心对象 `SsaFunctionIndex` 在模块函数集合稳定后构建，
持有：

- 规范化函数名到 `SsaFunction *` 的开放寻址表；
- `SsaFunction *` 到原始序号的常数时间映射；
- 每个函数的调用次数、被引用状态和叶函数状态；
- `function_epoch`，用于验证索引对应当前函数集合。

索引不拥有函数或符号字符串，只拥有表和计数数组。销毁模块或改变函数集合前
必须释放或失效索引。

### 数据流

1. SSA builder 先建立全部函数对象。
2. 建立名称索引，随后构建函数体；调用目标查找使用名称索引。
3. SSA 闭包稳定后，单次扫描所有 CALL/ICALL，批量生成调用计数、引用和叶函数
   事实。
4. 模块级优化读取这些事实；若内联或删除函数改变调用关系/函数集合，则增加
   epoch 并在下一个事实消费者前统一重建一次。
5. 函数级优化、寄存器分配和 lowering 保持现有顺序与语义。

不得在调用关系改变后继续读取旧事实。调试构建中 epoch 不匹配必须立即断言；
发布构建中走显式重建，不允许静默使用陈旧索引。

## 细分性能诊断

保留现有 `MIRA_COMPILE_PROFILE` 总开关，并进一步报告：

- SSA program build；
- mem2reg/SSA closure；
- reference analysis；
- module optimization；
- PHI destruction 与变量映射；
- register allocation；
- SSA lowering；
- machine IR optimization。

诊断关闭时只允许一次可预测分支，不得在热循环读取时钟。诊断输出不是公共
稳定接口，但字段名在本阶段测试中固定。

## 测试策略

所有生产改动遵循 RED--GREEN：

1. 单元测试先证明索引在不同插入顺序、碰撞、缺失符号、重复查询和 epoch
   失效下行为正确。
2. 复杂度测试使用计数钩子证明 800 函数/800 调用的名称比较次数为线性或
   近线性，并在旧实现上失败；不得只用易受噪声影响的墙钟时间作为 RED。
3. 端到端性能脚本测量 100/200/400/800，3 次预热、31 次正式样本并输出
   中位数、比例与产物大小。
4. O0--O3 checksum、IR 形态、fib、pressure、branch、stencil、vector_add
   和现有回归套件保持通过。
5. Windows 完成后在 Linux/SysV 重建编译器和 runtime，并复测 checksum 与
   800 函数编译门槛。

## 提交与回滚

细分计时、名称索引、调用事实批处理和事实扫描融合分别提交。每项可独立复测，
不得把无关重构混入性能提交。若某项无法满足 100 函数 1% 底线或引入运行/体积
退化，则回滚该项，不用其他测试的收益抵偿。

第一阶段完成条件是所有正确性底线通过且 Windows `gen_800 -O3` 中位数不高于
250 ms。若索引和安全扫描融合后仍未达到门槛，使用新的细分计时重新选取下一
热点，不提前引入线程池。
