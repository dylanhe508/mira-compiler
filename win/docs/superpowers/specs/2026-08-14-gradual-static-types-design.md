# Mira 渐进式静态类型增强设计

日期：2026-08-14

## 目标

让 Mira 已有的类型标注真正参与编译期检查和后端降级，同时保持未写类型的旧程序继续按当前推断规则工作。第一阶段解决“标注被解析器丢弃”和“SSA 默认猜成整数”两个根因，不借机引入泛型或重写整个类型系统。

## 用户可见语义

第一阶段支持六种语义类型：

- `unknown`：内部类型，仅表示旧代码尚未确定的类型，不能由用户显式书写。
- `i64`：64 位有符号整数。
- `f64`：64 位浮点数。
- `bool`：布尔值。
- `str`：字符串值。
- `void`：无返回值，只能作为函数返回类型，不能作为变量类型或普通表达式值。

函数参数、函数返回值以及 `let`/`mut` 声明可以带类型标注。显式标注是契约，编译器必须严格验证；没有标注的位置继续使用现有推断和兼容行为。

首期不做 `i64` 与 `f64` 的隐式转换。需要混合数值运算时，程序必须显式转换；这可以避免静默精度变化，也让 SSA 类型保持确定。

示例：

```mira
fn distance(x: f64, y: f64) -> f64 {
    math.sqrt(x * x + y * y)
}

fn main() -> void {
    let n: i64 = 3;
    let enabled: bool = true;
    io.println(n);
}
```

## 兼容原则

1. 未标注的旧源码不因为本次改动新增强制类型错误。
2. 只有用户写出的类型契约，以及能够从显式契约确定的使用点，触发严格检查。
3. 旧的表达式推断结果、内建调用兼容映射、内存所有权和优化语义保持不变。
4. Windows 与 Linux 使用相同的前端结构、检查规则和测试用例；平台运行时差异不得影响语言类型。
5. 本阶段不改变 ABI 的机器表示：`bool` 仍可沿用现有整数表示，`str` 沿用现有指针/字符串表示，但前端语义类型必须区分它们。

## 数据结构

在公共前端头文件中增加 `MiraType` 枚举，并提供：

- 类型名到 `MiraType` 的解析函数；
- `MiraType` 到诊断文本的格式化函数；
- 类型相容性判断函数；
- 从已有表达式/SSA 类型到语义类型的窄接口。

`Def` 保存每个参数的类型、参数是否显式标注、返回类型以及返回类型是否显式标注。外部函数声明使用同一套签名结构，避免普通函数和 `extern` 走两套互相漂移的规则。

局部声明节点保存声明类型和“是否显式标注”。解析器不得再只跳过类型 token。所有新增数组与字符串遵循现有 AST 生命周期统一释放。

## 编译流程

类型检查位于“所有模块解析完成”之后、“构建 SSA”之前：

```text
词法分析 -> 解析并保留类型 -> 汇总跨模块签名 -> 类型检查 -> SSA -> 优化 -> 代码生成
```

这样调用者可以检查其他模块中的函数签名，错误也能在进入 SSA 前报告，不会再由后端以 `INT` 默认值掩盖。

检查器分两步：

1. 签名收集：建立模块限定的函数/外部函数签名表，并检查未知类型名、非法 `void` 参数、重复或冲突声明。
2. 函数体检查：在局部环境中检查表达式、声明、赋值、调用和返回；表达式产生 `MiraType`，未标注且无法可靠确定时保留 `unknown`，以维持旧代码兼容。

检查通过后，将已验证的参数和返回类型传给 SSA 构建器。显式或可靠推断出的 `f64`、`bool`、`str`、`void` 不再被默认降为整数；仍为 `unknown` 的旧路径继续使用现有兼容降级。

## 检查规则

- 函数调用：参数数量必须匹配；实参类型必须与显式形参类型一致；显式返回类型决定调用表达式类型。
- 返回：显式 `void` 函数不能返回值；显式非 `void` 函数的尾表达式/现有返回形式必须产生相同类型；缺少结果时报错。
- 声明与赋值：初始化值和后续赋值必须符合显式声明类型；未标注变量以第一个可靠值推断，无法可靠推断时保持旧行为。
- 算术：数值运算要求两侧为相同数值类型；不自动混合 `i64` 与 `f64`。
- 比较：有序比较要求两侧为相同可比较类型，结果为 `bool`；相等比较要求类型相容，结果为 `bool`。
- 逻辑与条件：严格类型区域要求 `bool`；完全未标注的旧代码保留现有真值兼容语义。
- 字符串：字符串字面量为 `str`；字符串参数、返回值和变量不再与整数或普通指针混淆。
- 无值表达式：`void` 调用可以作为语句，不能用于初始化、赋值、算术、比较、参数值或函数结果。
- 分支：若分支值参与函数结果或表达式结果，所有可达分支类型必须一致；无法从旧代码可靠确定时不新增错误。

## 诊断

类型错误必须包含源码文件、行号、具体上下文、期望类型和实际类型，例如：

```text
sample.mira:8: argument 2 of 'distance': expected f64, got i64
sample.mira:12: cannot assign str to variable 'count' declared as i64
sample.mira:19: function 'log' returns void and cannot be used as a value
```

首个实现优先保证错误准确且稳定，不加入自动修复。未知类型名应在解析/签名阶段直接报错，不能退化成 `unknown`。

## 测试策略

严格采用测试先行：每类规则先加入失败测试，再写最小实现使其通过。

测试分为四层：

1. 解析与结构测试：参数、返回值、局部变量和 `extern` 的类型被完整保留。
2. 正例：六种类型、跨模块调用、尾表达式返回、显式 `void`、带类型与无类型代码混用。
3. 反例：参数、返回、赋值、算术、条件、分支和 `void` 值误用；同时核对诊断关键文本。
4. 回归与后端：现有测试全部通过；代表性程序在 O0、O1、O2、O3 下输出一致；Windows 与 Linux 都能构建并运行相同语义测试。

性能验收包括编译时间、产物大小和代表性运行基准。类型检查只在线性遍历 AST 和签名表查找中工作，不应改变已生成机器码；若类型信息使机器码变化，必须单独核对正确性和性能，不能用“类型增强”掩盖退化。

## 明确不在本阶段做的内容

- `list<T>`、泛型函数或泛型结构体；
- 联合类型、可空类型、类型别名和用户自定义转换；
- 基于控制流的完整高级类型推断；
- 隐式数值提升；
- 标准库 API 的破坏性重命名或重构；
- 与类型增强无关的 SSA 优化修改。

这些内容可在基础类型契约稳定后逐项设计，避免一次改动同时破坏语法、ABI、标准库和优化器。

## 完成标准

- 类型标注不再被丢弃，普通函数与 `extern` 都拥有可查询签名。
- 所有上述严格规则均有正反测试，错误位置和期望/实际类型清楚。
- 未标注旧测试不新增失败，现有语义和所有权行为不变。
- SSA 对已知 `i64`、`f64`、`bool`、`str`、`void` 使用正确类型，不再统一猜成整数。
- Windows/Linux 源码与测试同步，通过 O0-O3 正确性回归。
- 编译速度、产物大小和运行性能对比无不可解释退化。
